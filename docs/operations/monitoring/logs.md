# Logs

All Orion Platform 4.2 LTS components write structured logs in JSON format to standard output, one line per event, with no file logging. Collection, rotation and archiving are the responsibility of the infrastructure layer, not the application. This page describes the field schema, request correlation, masking of sensitive data and retention.

## Entry format

| Field | Type | Description |
| --- | --- | --- |
| `ts` | string (RFC 3339, UTC) | Timestamp with millisecond precision |
| `level` | string | `debug`, `info`, `warn`, `error`, `fatal` |
| `component` | string | `gateway`, `core`, `ledger`, `worker`, `scheduler`, `console` |
| `msg` | string | Concise English message, with no interpolated data |
| `request_id` | string (UUID) | Value of the `X-Orion-Request-Id` header, or generated by the gateway |
| `trace_id` | string (hex, 32 characters) | OpenTelemetry trace identifier |
| `tenant` | string | Tenant identifier |
| `order_id` | string | Populated only in the context of an order |
| `err_code` | string | Error code, for example `ORN-5002`, `ORN-5009`, `ORN-3001` |
| `duration_ms` | number | Operation handling time in milliseconds |

A sample entry from `orion-gateway`:

```json title="stdout / orion-gateway"
{"ts":"2026-02-11T09:14:22.481Z","level":"error","component":"gateway","msg":"upstream dependency unavailable","request_id":"5f2c1b64-8e0a-4d3f-9a11-77c0be31d902","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","tenant":"acme-retail","order_id":"ord_01HQ8ZK4","err_code":"ORN-5002","duration_ms":5012,"method":"POST","endpoint":"/orders","status":503}
```

!!! note "No interpolation in `msg`"
    The `msg` field must be a constant string so that entries can be grouped. Variable values go into separate fields. The LogQL rules and Elasticsearch queries in this documentation assume this convention.

## Log levels

| Level | When to use | Typical volume |
| --- | --- | --- |
| `debug` | Diagnosing a single problem, temporarily only | 20-50x `info` |
| `info` | Default in `prod`; business and lifecycle events | baseline |
| `warn` | Retries, degradation, approaching limits | 1-5% of `info` |
| `error` | Failed operation with an `ORN-*` code | < 0.5% of `info` |
| `fatal` | Process shutdown; precedes a pod restart | isolated entries |

The level is set by `ORION_LOG_LEVEL` and the format by `ORION_LOG_FORMAT` (`json` in `staging` and `prod`, `text` acceptable in `dev`). Full list: [environment variables](../../getting-started/configuration/environment-variables.md).

Changing the level without restarting the process:

```bash
kubectl exec -n orion deploy/orion-gateway -- \
  orion config set log.level debug --ttl 15m
```

```text
level set to "debug" for 15m0s (reverts to "info" at 2026-02-11T09:31:04Z)
```

!!! warning "Debug level in production"
    `debug` increases log volume by tens of times and can fill the collector agent's buffer. Always use the `--ttl` parameter with a value no longer than 15 minutes, and only on a single replica.

## Collecting logs

=== "Kubernetes"

    ```bash
    # current logs of a single replica
    kubectl logs -n orion deploy/orion-gateway --tail=200

    # all replicas of a component, live
    kubectl logs -n orion -l app.kubernetes.io/name=orion-worker -f --max-log-requests 12

    # logs of the previous instance after a restart
    kubectl logs -n orion orion-core-7d9f8b6c4d-x2kqp --previous
    ```

=== "Docker Compose"

    ```bash
    docker compose logs --tail=200 orion-gateway
    docker compose logs -f --since 15m orion-worker orion-core
    docker compose logs orion-ledger | jq -c 'select(.level=="error")'
    ```

=== "System packages"

    ```bash
    journalctl -u orion-gateway -n 200 --no-pager
    journalctl -u orion-worker --since "15 min ago" -o cat | jq -c 'select(.err_code!=null)'
    journalctl -u orion-gateway -f -o cat
    ```

In installations from system packages the logs are captured by `systemd-journald` and then exported by a Promtail or Filebeat agent. The unit configuration is described in the [bare metal installation](../../getting-started/installation/bare-metal.md).

## Request correlation

The gateway generates a `request_id` for every request that arrives without an `X-Orion-Request-Id` header and passes it on to `orion-core`, `orion-ledger` and, in a Kafka event header, to `orion-worker`. As a result, a single query reconstructs the entire path from the API to webhook delivery.

```logql
{namespace="orion"}
  | json
  | request_id = "5f2c1b64-8e0a-4d3f-9a11-77c0be31d902"
  | line_format "{{.ts}} {{.component}} {{.level}} {{.msg}} {{.err_code}} {{.duration_ms}}ms"
```

Sample output:

```text
2026-02-11T09:14:17.402Z gateway info  request accepted            12ms
2026-02-11T09:14:17.418Z core    info  order created draft         31ms
2026-02-11T09:14:17.602Z ledger  info  payment intent registered   163ms
2026-02-11T09:14:17.771Z core    info  order pending_payment        9ms
2026-02-11T09:14:22.481Z gateway error upstream dependency unavailable ORN-5002 5012ms
2026-02-11T09:14:23.115Z worker  warn  webhook retry scheduled      —
```

The Elasticsearch equivalent:

```bash
curl -s "https://logs.internal.example.com/orion-*/_search" \
  -H 'Content-Type: application/json' -d '{
    "query": {"term": {"request_id": "5f2c1b64-8e0a-4d3f-9a11-77c0be31d902"}},
    "sort": [{"ts": "asc"}], "size": 100
  }' | jq -r '.hits.hits[]._source | "\(.ts) \(.component) \(.msg)"'
```

!!! tip "From the customer to the log"
    The `X-Orion-Request-Id` header is returned in every API response. Asking the customer for that value from their report takes you straight to a specific execution path without guessing the time window.

## Masking sensitive data

The logging layer masks values before serialization. Masking is unconditional and cannot be disabled in the `staging` and `prod` profiles.

| Field / pattern | Masking method |
| --- | --- |
| Card number (PAN) | removed entirely, replaced with `[redacted:pan]` |
| Email address | `a***@example.com` |
| `Authorization` header | `Bearer [redacted]` |
| `X-Orion-Key` header | `[redacted:apikey]` |
| `POST /payments` request body | field names only, without values |
| Bank account number | last 4 characters, the rest as `*` |

!!! danger "Never log a full request body"
    Adding raw request body logging to `orion-ledger` violates the PCI DSS requirements described in [security](../security.md) and requires a security incident report. Use `trace_id` and the diagnostic bundle for troubleshooting instead.

## Retention and archiving

| Tier | Scope | Retention |
| --- | --- | --- |
| Loki / Elasticsearch (hot) | all levels | 30 days |
| S3 archive `s3://orion-artifacts/logs/` | `warn`, `error`, `fatal` | 400 days |
| Audit log (`audit` schema) | data change events | 400 days |

Archiving runs as an `orion-scheduler` job named `log-archive`, executed daily at 02:30 UTC. To verify the last run:

```bash
kubectl exec -n orion deploy/orion-scheduler -- orion diag bundle --dry-run --job log-archive
```

## Diagnostic bundle

Attach a bundle collected with `orion diag bundle` to support tickets. It contains the last hour of logs, a metrics snapshot, the output of `orion config validate` and `orion db status`, with no personal data or secrets.

```bash
orion diag bundle \
  --since 1h \
  --components gateway,core,worker \
  --include-metrics \
  --out /tmp/orion-diag-$(date -u +%Y%m%dT%H%M%SZ).tar.gz
```

```text
collecting logs        gateway(3), core(2), worker(6)   ok
collecting metrics     snapshot 9100/metrics x11        ok
config validate        /etc/orion/orion.yaml            ok
db status              schema core=4.2.1 ledger=4.2.1   ok
redacting              pan, email, authorization        42 hits
written /tmp/orion-diag-20260211T091840Z.tar.gz (18.4 MiB)
```

Upload the bundle to the `https://support.nimbus.example.com` portal; the ticketing rules are described in [support](../../support.md).
